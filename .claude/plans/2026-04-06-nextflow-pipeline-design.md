## Problem Statement

Every imaging lab on an HPC cluster writes the same SGE boilerplate by hand: illumination correction jobs, segmentation jobs, feature extraction jobs, dependency chains, scratch staging, container execution. cptools2 already automates this for CellProfiler on Eddie, but the current architecture is a Python tool that generates shell scripts — it's Eddie-specific, CellProfiler-specific, and the orchestration layer is homegrown code that duplicates what workflow engines already do.

The goal is to transform cptools2 into an assay-agnostic, multi-stage imaging pipeline that runs on Eddie (primary target) with multi-cluster readiness. Illumination correction, nuclear and cell segmentation, and feature extraction (DeepProfiler, DINOv2, future models) all orchestrated from a single YAML config.

## What Makes This Cool

No production-ready Nextflow pipeline for Cell Painting exists. The Broad's pipelines use WDL on Terra (cloud). nf-core/mcmicro targets multiplexed imaging and is still pre-release. Every other lab writes manual shell scripts.

cptools2 + Nextflow would be the first tool that lets a researcher go from raw microscopy images to single-cell feature embeddings with one command, on an HPC cluster, with plug-and-play model swapping. The Python companion library handles the hard data preparation (ImageXpress filename parsing, LoadData CSV generation, plate-aware splitting) that no workflow engine understands natively.

## Constraints

- **Eddie is the primary target.** Multi-cluster (SLURM, PBS) is a future benefit of the architecture, not a development priority.
- **Eddie-specific SGE quirks must work**: `h_rss` (not `h_vmem`), `-pe gpu-a100` for GPUs, `-q staging` for DataStore access, `hold_jid` with job names not IDs, `SINGULARITY_TMPDIR` on scratch.
- **Assay-agnostic**: channels configurable via YAML, not hardcoded to 5 Cell Painting channels. Supports fluorescent and brightfield.
- **Containers only on ai-update branch.** Master retains conda-based workflow.
- **Polars over pandas** for internal DataFrame operations (CSV joins, LoadData generation). Migration is phased — existing pandas code works, polars is the target for `ai-update`.

## Premises

1. **Configurable channels via YAML** — not hardcoded to 5 Cell Painting channels. Any fluorescent or brightfield assay.
2. **Segmentation is core, not optional** — supports both nuclear and cell body segmentation, configurable per workflow. Feeds both DeepProfiler (centroids) and CellProfiler (morphology measurements).
3. **Illumination correction and segmentation are the bedrock** — good data requires good preprocessing. These aren't steps to skip, they're steps to get right.
4. **Hybrid architecture** — Python companion library for data preparation + Nextflow for orchestration. Not a custom Python workflow engine.
5. **Assay-agnostic** — Cell Painting is the first workflow, not the only one. Brightfield, other fluorescent assays, different channel configurations.
6. **Manifest-driven container system** — adding new tools (DINOv2, Cellpose, future models) is a JSON + config change, not Python code changes.
7. **Eddie first, multi-cluster ready** — development and testing targets Eddie SGE. Nextflow executor profiles give SLURM/PBS/local for free, but Eddie is the priority.

## Approaches Considered

### Approach A: Nextflow-First Full Rewrite
Replace generate_scripts.py entirely with Nextflow DSL2. cptools2 becomes a thin CLI that invokes `nextflow run`. Maximum Nextflow, minimum Python.

- Effort: L
- Risk: Medium (Eddie SGE executor needs validation)
- Pro: cleanest architecture, full Nextflow benefits
- Con: steep learning curve, less Python control

### Approach B: Ship Python Now, Nextflow Later
Execute original 6-phase plan, then port orchestration to Nextflow as a separate effort.

- Effort: XL (double work)
- Risk: Low initially, but builds throwaway code
- Pro: ships fastest, all Python
- Con: custom orchestrator becomes waste when Nextflow arrives

### Approach C: Nextflow Core + cptools2 Companion Library (Chosen)
Nextflow pipeline for orchestration. cptools2 refactored as a Python companion library for data preparation. CLI wraps `nextflow run` with user-friendly config.

- Effort: L
- Risk: Medium (Nextflow SGE on Eddie needs validation)
- Pro: preserves all Python code, no throwaway work, multi-cluster ready
- Con: two languages (Python + DSL2)

## Recommended Approach

**Approach C: Nextflow Core + cptools2 Companion Library.**

cptools2's Python code is already good at image discovery, LoadData CSV generation, metadata enrichment, and plate-aware splitting. That stays. What gets replaced is `generate_scripts.py` and the proposed `cptools2/stages/` module — Nextflow handles job scheduling, container execution, dependency chains, retries, and caching.

### Architecture

```
cptools2/                          # Python companion library
  filelist.py                      # Image discovery, plate layout detection
  loaddata.py                      # LoadData CSV generation (polars)
  splitter.py                      # Chunk and per-plate splitting
  containers.py                    # Manifest-based container resolution
  utils.py                         # Shared utilities
  file_tools.py                    # CSV joining and metadata enrichment
  colours.py                       # Terminal output formatting
  parse_yaml.py                    # YAML config → structured params
  __main__.py                      # CLI: prepare, pipeline, join

nextflow/                          # Nextflow pipeline
  main.nf                          # Pipeline entry point
  nextflow.config                  # Executor profiles (eddie, slurm, local)
  modules/
    illum_calculate.nf             # Illumination correction (calculate)
    illum_apply.nf                 # Illumination correction (apply)
    segmentation.nf                # Nuclear + cell body segmentation
    feature_extract.nf             # DeepProfiler / DINOv2 / future models
    qc_report.nf                   # Post-stage quality checks
  conf/
    eddie.config                   # Eddie SGE: h_rss, gpu-a100, staging
    slurm.config                   # SLURM (future)
    containers.config              # Container paths per profile

cptools2/dockerfiles/              # Dockerfiles in repo
  Dockerfile.deepprofiler
  Dockerfile.cellpose
  README.md

cptools2/templates/                # CellProfiler pipeline templates
  illum_calculate.cppipe
  illum_apply.cppipe
  nuclear_segmentation.cppipe
  cell_segmentation.cppipe         # Cell body segmentation (new)
```

### How It Works

```
User runs: cptools2 pipeline config.yml

cptools2 CLI:
  1. Parses YAML config
  2. Discovers images (filelist.py)
  3. Generates LoadData CSVs (loaddata.py + splitter.py)
  4. Resolves containers (containers.py + manifest)
  5. Generates nextflow params JSON
  6. Invokes: nextflow run nextflow/main.nf -params-file params.json -profile eddie

Nextflow handles:
  - Job scheduling (SGE array jobs on Eddie)
  - Container execution (singularity exec with --nv for GPU)
  - Stage dependencies (illum → seg → extract)
  - Retries on failure
  - Caching (resume from last completed stage)
  - Resource allocation (h_rss, slots, GPU PE)
```

### Eddie Profile (`conf/eddie.config`)

**NOTE: This config is proposed, pending validation on Eddie. The SGE executor's support
for `clusterOptions` with `h_rss` and `gpu-a100` PE must be tested with a trivial pipeline
before committing to this approach. Fallback: custom executor script or direct `qsub` wrapper.**

```groovy
profiles {
    eddie {
        process {
            executor = 'sge'
            penv = 'sharedmem'
            clusterOptions = "-l h_rss=${task.memory.toGiga()}G"  // double-quoted for GString interpolation

            withLabel: 'gpu' {
                penv = 'gpu-a100'
                clusterOptions = "-l gpus=1 -l h_rss=${task.memory.toGiga()}G"
                containerOptions = '--nv'
            }

            withLabel: 'staging' {
                queue = 'staging'
                penv = false  // omit PE entirely — staging queue incompatible with sharedmem
            }

            withLabel: 'illum_calculate' {
                cpus = 4
                memory = '16 GB'  // per slot, 64GB total
            }

            withLabel: 'illum_apply' {
                cpus = 1
                memory = '4 GB'
            }

            withLabel: 'segmentation' {
                cpus = 1
                memory = '4 GB'
            }

            withLabel: 'feature_extract' {
                cpus = 1
                memory = '16 GB'
            }
        }

        singularity {
            enabled = true
            autoMounts = true
            runOptions = '--bind /exports/eddie/scratch/$USER:/exports/eddie/scratch/$USER'
        }

        env {
            SINGULARITY_TMPDIR = '/exports/eddie/scratch/$USER/singularity_tmp'
        }
    }
}
```

### YAML Config (user-facing)

```yaml
# Experiment
experiment: /path/to/imagexpress/experiment
# OR:
add plate:
  - experiment: /path/to/experiment
    plates: [plate_1, plate_2]

# Channels (assay-agnostic)
channels:
  - name: DNA
    stain: Hoechst 33342
  - name: RNA
    stain: SYTO 14
  - name: ER
    stain: Concanavalin A
  # ... configurable per assay

# Pipeline stages (all optional, run what you list)
stages:
  - illum_calculate
  - illum_apply
  - segmentation
  - feature_extraction

# Segmentation config
segmentation:
  type: nuclear          # nuclear | cell | both
  min_diameter: 20
  max_diameter: 80
  method: otsu

# Feature extraction
feature_extraction:
  tool: deepprofiler     # role name → looked up in manifest
  # OR: tool: dinov2

# Chunking
chunk: 96

# Paths
location: /exports/eddie/scratch/$USER/project
commands location: /exports/eddie/scratch/$USER/project/commands

# Containers (optional — defaults from CPTOOLS2_CONTAINER_DIR + manifest)
container_path: /exports/.../containers/cellprofiler_4.2.8.sif

# Post-analysis
join_files:
  - Image.csv
  - Cells.csv
data_destination: /path/to/datastore/project
```

### CLI Commands

```bash
# Full pipeline (generates + runs Nextflow)
cptools2 pipeline config.yml                    # all stages
cptools2 pipeline config.yml --stages illum     # alias: runs illum_calculate + illum_apply
cptools2 pipeline config.yml --dry-run          # generate params, don't run

# Data preparation only (no Nextflow)
cptools2 prepare config.yml                     # generate LoadData CSVs, filelists

# Existing commands
cptools2 generate config.yml                    # legacy: standalone CellProfiler workflow
cptools2 join --location /path --patterns ...   # join chunked CSVs

# Nextflow resume (after failure)
cptools2 pipeline config.yml --resume           # Nextflow resumes from last checkpoint
```

### Stage Name Vocabulary

| CLI alias | Stages run |
|---|---|
| `illum` | `illum_calculate` + `illum_apply` |
| `segment` | `segmentation` |
| `extract` | `feature_extraction` |
| `all` (default) | all stages in order |

Individual stage names (`illum_calculate`, `illum_apply`, `segmentation`, `feature_extraction`) also accepted for fine-grained control.

### Modules Superseded by Nextflow

The following existing modules are **replaced** by Nextflow on `ai-update` and will not be extended:
- `generate_scripts.py` — SGE script generation (Nextflow handles this)
- `job.py` — batch planning and command orchestration (Nextflow handles scheduling)

These files remain on `master` for the legacy conda workflow.

The following existing module needs **extension** (already exists, not new):
- `containers.py` — manifest-based container resolution already implemented; needs `is_gpu_container()` and support for arbitrary manifest roles
- `parse_yaml.py` — `check_yaml_args()` must be extended to accept new YAML keys: `channels`, `stages`, `segmentation`, `feature_extraction`

### Resume and Idempotency

- `cptools2 pipeline config.yml --resume` skips data preparation (uses existing `params.json` from prior run) and passes `-resume` to Nextflow, which restarts from the last cached checkpoint.
- Without `--resume`, data preparation re-runs (idempotent — overwrites existing LoadData CSVs and filelists) and Nextflow starts fresh.

### Error Handling

- If `nextflow` is not on PATH: CLI prints "Nextflow not found. Install with: `curl -s https://get.nextflow.io | bash`" and exits with code 127.
- If Nextflow exits non-zero: CLI surfaces the Nextflow error log path and suggests `--resume`.

### Testing Strategy

- **Python library**: existing pytest suite (84+ tests) covers filelist, loaddata, splitter, containers, utils, file_tools
- **Nextflow pipeline**: test with `-profile local` (local executor, Docker containers) for CI. Eddie profile tested manually on Eddie.
- **Integration tests**: `cptools2 pipeline --dry-run` generates params.json without invoking Nextflow — verifiable in CI

### Nextflow Installation Contingency

If Eddie does not provide a Nextflow module:
1. Install to `$HOME/.local/bin`: `curl -s https://get.nextflow.io | bash && mv nextflow ~/.local/bin/`
2. Java: Eddie provides `module load java`. Nextflow requires Java 11+.
3. Fallback: run Nextflow inside a container itself (`singularity exec nextflow.sif nextflow run ...`)

## Open Questions

1. **Nextflow SGE executor on Eddie**: Does the SGE executor support `h_rss` via `clusterOptions`? Does it handle the `-pe gpu-a100` parallel environment correctly? Needs validation with a simple test pipeline.
2. **Nextflow installation on Eddie**: Is Nextflow available as a module, or does it need to be installed in user space? Java runtime needed.
3. **Staging queue integration**: Eddie's staging queue (`-q staging`) for DataStore access is incompatible with `-pe sharedmem`. How does Nextflow handle queue-specific PE restrictions?
4. **CellProfiler pipeline templates**: Should `.cppipe` files be static templates with string substitution, or should cptools2 generate them dynamically based on channel config? Dynamic generation is more flexible but harder to inspect in CellProfiler GUI.
5. **QC reporting**: What format? HTML report per stage? Nextflow's built-in reporting? Custom Python QC module?

## Success Criteria

- `cptools2 pipeline config.yml` runs the full pipeline on Eddie from raw images to feature embeddings
- Nextflow handles job scheduling, retries, container execution, and resume-from-failure
- Channel configuration is YAML-driven, not hardcoded
- Adding a new feature extraction model requires only a manifest entry + config change
- All existing Python utilities (filelist, loaddata, splitter) work with polars
- 84+ tests pass
- A cross-group collaborator at Edinburgh can install cptools2, write a YAML config, and run their imaging pipeline on Eddie without writing any shell scripts
